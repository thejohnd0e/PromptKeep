## Source URL (2026-09-14)

### What
The full page URL (e.g. `https://chatgpt.com/g/g-p-.../c/...`) is captured from
`location.href` and written into the PNG as a single dedicated field:
- **`Source` tEXt chunk** → ExifTool shows `PNG:Source`

**Not** written to `parameters` — mixing the URL into the prompt text produced a
glued string in Eagle's SD Metadata panel, so `parameters` stays prompt-only.

## Confirmed Decisions

### ExifTool `caBX` + `eXIf` conflict

Root cause: ExifTool uses a **shared `PROCESSED` offset map** across independent PNG chunks. Both `caBX` (JUMBF) and `eXIf` (TIFF) start at offset 0, so ExifTool falsely reports one referencing the other's directory.

- **Issue**: https://github.com/exiftool/exiftool/issues/452 (open, unfixed in 13.59)
- **Fix PR**: https://github.com/exiftool/exiftool/pull/453 (open, unmerged)
- **Regression**: introduced in 12.51, commit `3de0f8ce`

**Our fix**: `insertPngMetadata()` in `png-writer.ts` skips `eXIf` when `hasCabx === true`. XMP `iTXt` is immune (no TIFF offsets). For regular PNGs without `caBX`, EXIF is still written normally.

Evidence:
- `test.png` (original): ExifTool shows `IFD0 pointer references previous JUMBFBox directory`
- `test-cabx-only.png` (no EXIF, valid XMP): ExifTool shows **0 warnings**, prompt visible
- `test-enriched-fixed.png` (new writer): `AIPromptInformation = ExifTool compatibility prompt`, `AISystemUsed = ChatGPT`

### XMP `iTXt` malformed chunk

Writer was emitting 4 control bytes after keyword (`keyword\0\0\0\0\0...`) instead of 5 (`keyword\0\0\0\0\0\0...`). The fifth byte is the **compression method** field, mandatory per PNG spec even when compression flag = 0.

**Fix**: `buildXmpItxtChunk()` now writes 5 bytes; `parseItxtXmp()` always reads the compression method byte; `makeItxt()` fixture generates correct format.

### PNG textual tags

Official writable PNG TextualData tags (from ExifTool PNG.pm): `Title`, `Author`, `Description`, `Copyright`, `Creation Time`, `Software`, `Disclaimer`, `Warning`, `Source`, `Comment`, `Collection`, plus unregistered: `Artist`, `Document`, `Label`, `Make`, `Model`, `parameters`, `create-date`, `modify-date`, `TimeStamp`, `URL`.

## New Idea: `parameters` tEXt for Eagle Compatibility

### Context

User wants ChatGPT-generated PNGs to write metadata in the same field Stable Diffusion uses (`tEXt` chunk, keyword `parameters`), so Eagle can ingest prompts without a custom plugin.

### Investigation Results

**Stable Diffusion `parameters` format** (from `Stable Diffusion.png` sample):
- Chunk type: `tEXt` (uncompressed, Latin-1)
- Keyword: `parameters` (lowercase)
- Payload: Automatic1111 infotext format
- Structure: `<positive prompt>\nNegative prompt: <negative>\nSteps: 20, Sampler: Euler a, ...`

**Does Eagle read `parameters` natively?**
- **NO.** Eagle is closed-source and has no native PNG text chunk reader.
- Eagle's metadata model is **database-centric** (annotations/tags stored in Eagle DB, not file chunks).
- The Eagle plugin ecosystem exists precisely because Eagle doesn't parse SD metadata natively.
- Official Eagle support: "Eagle completely preserves all metadata information when processing images" = preservation on import/export, NOT parsing/display.
- Multiple SD-metadata plugins exist (10K+ downloads) to bridge this gap.

**Consequence**: Writing `parameters` tEXt alone will NOT make Eagle show prompts natively. It would be useful for:
1. A1111 PNG Info readability
2. CivitAI / sd-parsers / prompt reader ecosystem
3. Future Eagle plugin that reads the field
4. Cross-tool interop

### Pending Decision

To discuss with user: whether to add `parameters` tEXt anyway (for ecosystem interop) or keep the current XMP-only approach (which already works in ExifToolGUI). The Eagle plugin would still be needed either way.

## `parameters` tEXt Implementation (2026-09-14)

### Format
```
<prompt text>
```
Just the raw prompt. No SD-specific fields (Steps, Sampler, Model) — ChatGPT doesn't have them.

### Technical details
- **Chunk type**: `tEXt` (Latin-1) or `iTXt` (UTF-8 fallback for non-Latin-1 prompts)
- **Keyword**: `parameters` (lowercase, matching A1111 convention)
- **Builder**: `buildParametersText(prompt, system)` in `png-writer.ts`
- **Insertion**: Before first IDAT, alongside XMP `iTXt` and optional `eXIf`
- **Replacement**: Existing `parameters` chunks are replaced (not duplicated)

### Dual-channel metadata output
| Channel | Field | Visible in |
|---------|-------|-----------|
| XMP `iTXt` | `AIPromptInformation`, `AISystemUsed`, `DigitalSourceType` | ExifTool, ExifToolGUI, IPTC tools |
| PNG `tEXt` | `parameters` | A1111 PNG Info, CivitAI, Eagle SD Metadata plugin |

### Eagle compatibility — CONFIRMED WORKING (2026-09-14)
Eagle does NOT natively read PNG text chunks. However, the existing **"Stable Diffusion Metadata"** Eagle plugin (10K+ downloads) reads the `parameters` tEXt chunk. By writing our prompt into this field, users can install that plugin and see ChatGPT prompts alongside SD-generated images.

**User verification**: Eagle displays the prompt correctly via the SD Metadata plugin. No custom Eagle plugin needed.

### Bug fix: `iTXt` vs `tEXt` for `parameters` (2026-09-14)
**Problem**: When prompt contains non-Latin-1 characters (Cyrillic, CJK, emoji), code wrote `parameters` as `iTXt` chunk. ExifTool reads `PNG:Parameters` only from `tEXt` chunks.

**Root cause**: `buildParametersChunk` had two code paths — `tEXt` for Latin-1, `iTXt` for non-Latin-1. ExifTool's `PNG::TextualData` table is shared by both chunk types, but the `parameters` keyword wasn't being recognized in `iTXt`.

**Fix**: Always write `tEXt` for `parameters`. UTF-8 bytes in `tEXt` cause mojibake in ExifTool for non-Latin-1 characters, but:
- Full prompt is preserved in XMP `iTXt` (UTF-8, correct)
- Eagle SD Metadata plugin reads raw bytes from `tEXt`
- This matches A1111/Pillow behavior (tEXt with Latin-1 fallback)

**Also fixed**: `outputLength` calculation didn't account for existing `parameters` chunk replacement → `PNG_TRUNCATED` error on re-processing.

### Troubleshooting
If `PNG:Parameters` is missing in newly downloaded files:
1. Open `chrome://extensions`
2. Click **Refresh** (reload icon) on the extension
3. Download again
Chrome caches the built extension; a refresh forces it to reload the new build.

## Cyrillic in `parameters` — RESOLVED

`parameters` is written as a single **`iTXt` (UTF-8)** chunk. No `tEXt` copy is emitted,
so there is exactly one `PNG:Parameters` value and it is never mojibake.

| Chunk | Encoding | Value for `Create image алина` |
|-------|----------|-------------------------------|
| `iTXt` | UTF-8 | `Create image алина` ✅ |

ExifTool 13.59 reports `PNG:Parameters` once, with correct Cyrillic.

### Why the earlier `tEXt` attempt failed
PNG `tEXt` is ISO-8859-1 only, so UTF-8 bytes decode as mojibake (`Ð°Ð»Ð¸Ð½Ð°`).
Writing `parameters` as `iTXt` fixes the encoding.

### Earlier false conclusion (corrected)
A previous attempt concluded "ExifTool cannot read `parameters` from `iTXt`". That was
wrong: the iTXt builder was **missing the mandatory compression-method byte** (it wrote
4 control bytes after the keyword instead of 5), so ExifTool treated the chunk as opaque
`InternationalText`. With the byte present, `PNG:Parameters` resolves from `iTXt`.

iTXt layout after the chunk header: `keyword NUL flag method language NUL translated NUL text`.

### Compatibility note
Tooling that scans **only** `tEXt`/`zTXt` (some Stable Diffusion readers) will not see
this chunk. That trade-off is deliberate: correct Cyrillic was requested over that
narrower reader set. XMP `iTXt` (`AIPromptInformation`) remains the standards-compliant
channel for the full prompt.
